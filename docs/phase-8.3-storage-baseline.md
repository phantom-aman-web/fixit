# Phase 8.3 Storage Baseline Report

## Existing Storage Architecture

### Provider Abstraction
The application already has a well-defined storage interface in `src/lib/providers/index.ts`:
```typescript
export interface StoredFile {
  key: string;
  fileName: string;
  mimeType: string;
  sizeBytes: number;
}

export interface StorageProvider {
  save(buffer: Buffer, fileName: string, mimeType: string): Promise<StoredFile>;
  read(key: string): Promise<{ buffer: Buffer; fileName: string; mimeType: string } | null>;
  delete(key: string): Promise<void>;
  publicUrl(key: string): string;
}
```
Currently, `LocalStorageProvider` (`src/lib/providers/storage.ts`) implements this by writing to a local `uploads/` directory using random UUIDs for keys.

### Database File Metadata
The Prisma schema includes dedicated models for file tracking. Files are stored by their storage keys, not long-lived URLs.
- **ProblemMedia**: `url` (storage key), `fileName`, `mimeType`, `sizeBytes`, `type`
- **TechnicianDocument**: `fileName`, `storageKey`
- **RepairInspection**: `photosJson` (JSON array of media keys)

### API Upload Routes
- **`POST /api/problems/[id]/media`**: Accepts base64, validates MIME (images/video), limits to 10MB, saves via `storage.save()`, and inserts a `ProblemMedia` record. Validates customer ownership.
- **`POST /api/technician/documents`**: Accepts base64, validates MIME (images/pdf), limits to 5MB, saves via `storage.save()`, and inserts a `TechnicianDocument` record. Validates technician ownership.
- **`GET /api/uploads/[id]`**: Retrieves files via `storage.read()`. Implements strict authorization checking: verifying the caller is the owner (Customer), the assigned Technician, or an Admin.

### Image Analysis Flow
- **`POST /api/ai/image`**: Currently accepts raw base64 data URLs from the client, validates size (5MB limit) and MIME type, and passes them directly to `analyzeImage()` (Gemini).
- To comply with the Phase 8.3 instructions ("User uploads image -> Server validates image -> Supabase Storage -> Authorized retrieval -> Gemini"), this route will be modified to accept a `mediaId` (referencing an already uploaded `ProblemMedia`), fetch the file buffer securely from the StorageProvider, and pass that securely to Gemini.

### Key Security & Authorization Findings
- **IDOR Protection exists**: `GET /api/uploads/[id]` manually checks relationships in the database before serving the file.
- **Path Traversal Protection exists**: `safeKey()` enforces `^[a-zA-Z0-9-]+$` on the storage keys.
- **Database consistency**: We do not store temporary signed URLs as permanent state, which is correct. We just store the `key`.

## Implementation Strategy for Supabase Storage

1. **New Provider**: Create `SupabaseStorageProvider` implementing `StorageProvider`.
2. **Environment Variables**: Use `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_STORAGE_BUCKET`.
3. **Bucket Layout**: Enforce safe paths internally inside the provider (e.g., `problems/{userId}/{problemId}/{key}` or `technicians/{userId}/{key}`).
4. **Signed URLs**: Instead of streaming the buffer through the Next.js server on download (which consumes bandwidth), we can modify `publicUrl` to return a short-lived signed URL generated by the Supabase admin client, reducing server load. Alternatively, we keep `read()` returning a buffer for Gemini compatibility and `GET /api/uploads/[id]` can redirect to a signed URL or stream it.
5. **Preserving existing logic**: 
    - Supabase will be chosen via `STORAGE_PROVIDER=supabase` in environment config. 
    - The existing `LocalStorageProvider` will remain intact as a fallback for local development.
